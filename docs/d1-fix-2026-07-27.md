## The fix

The dashboard previously rendered
`advisorView.accounting.advisorUsage.wakeCount` against the reactive budget.
`wakeCount` is `claims.length` (`packages/kernel/src/advisor.ts:302`): every
claimed wake, including the reserved retrospective and wakes that consumed no
unit at all. That is how run 2 of the independent pass produced the reading
"Wakes used: 3 of 2 reactive".

The fix is the minimal UI-only change the report specified. `app.tsx` now
derives the consumed reactive count from the ledger the client already
receives, using the same predicate as the authoritative
`AdvisorService.consumedWakeUnits`
(`packages/service/src/advisor/service.ts:626`): only `wake_outcome` rows with
`modelStarted === true` and `purpose === "advisor_observation"`. The
derivation lives at `packages/ui/src/app.tsx:246` (constant
`reactiveWakesUsed`) and the state line at `packages/ui/src/app.tsx:866`
renders it. The "reserved retrospective" half of the line remains the static
budget, which is the report's first suggested option.

No field was added to `AdvisorUsageReport` or the contracts. The UI-only fix
is sufficient because `GET /api/runs/:id/advisor` already returns the raw
sidecar rows as `ledger` (`packages/service/src/server.ts:414`), so the client
has everything the service predicate needs.

With the fix, the two independent-test runs would have rendered "1 of 2" and
"2 of 2" respectively instead of "2 of 2" and "3 of 2" (each run also consumed
its reserved retrospective, which no longer counts against the reactive
budget).

## Regression coverage, and proof that it bites

The V-11 browser harness (`packages/ui/test/a11y.ts`, block starting at line
331) now fabricates the exact conflating ledger on its adviser-enabled run,
appending through the real `AdvisorSidecar.append` API so the sidecar hash
chain stays valid: three `wake_claimed` rows plus three `wake_outcome` rows —
one consumed reactive observation, one consumed reserved retrospective, and
one preflight-blocked wake with `modelStarted: false`. Three wakes are claimed
but only one reactive unit is spent. The harness asserts the rendered line
reads "Wakes used: 1 of 2 reactive + 1 reserved retrospective" after a
same-sequence publish (it first asserts the "0 of 2" baseline, so the change
in the counter also re-proves the sidecar refetch).

The fixture discriminates all three plausible wrong predicates: counting
claims renders 3, counting every guarded model start renders 2, and counting
observation-purpose outcomes regardless of `modelStarted` also renders 2; the
harness accepts only 1.

Mutation check: with the old `wakeCount` render temporarily restored, the
harness fails at exactly the final wait (the page shows "3 of 2", reproducing
the reported symptom verbatim); with the fix restored it passes. Both runs
were performed and observed in this pass.

## Follow-up: deterministic retry-accounting test

The independent report flagged "retry after a recoverable Action Needed state
does not double-charge" as untested against real providers. The new
`packages/service/test/real-runner-retry.test.ts` pins the coordinator-side
contract deterministically, using injected provider ports (the same pattern as
the existing runner integration test):

- Both openings succeed, then the Codex candidate burst throws a recoverable
  transport error whose message deliberately matches no limit, billing, or
  context-window pattern. The run pauses on the generic
  "Collaboration paused after a codex failure" card with
  `["Retry collaboration", "Cancel"]` and two usage rows recorded.
- The test then appends the identical `human_override`
  (`decision: "retry_collaboration"`) the coordinator records for that button
  and re-enters `runner.run`.
- It asserts: the re-executed candidate is claimed as a `resumed` event on a
  new ready item (`readyWorkId` differs from the failed claim's) with
  `chargeBudget: false`; exactly 6 of the 7 model wakes charged the provider
  budget, so the re-executed stage is not charged twice; the re-executed burst
  lands as a distinct usage row causally bound to the resumed claim; the two
  pre-failure rows are byte-identical afterwards; the failed invocation's
  ready item never acquires a usage row; and the run ends
  `completed_consensus` with the overhead gate passing, zero uncaused
  invocations, a drained ready queue, and an intact hash chain.

If a future change made the retry reuse the original invocation key with
different counters, the kernel's `USAGE_INVOCATION_KEY_REUSED` guard would
fail the run and this test; silent overwriting, budget double-charging, and
ready-item reuse are each caught by their own assertion.
